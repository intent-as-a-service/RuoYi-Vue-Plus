# 意图即服务 · 接入指南

> 给业务研发看的操作手册：**新增一个意图，一共三步，平台代码零改动。**
> 典型成本 1 ~ 1.5 人日/意图（不含梳理业务逻辑本身）。

---

## 0. 心智模型：一个意图 = 三份声明

```
① 宿主工具（Java，1~3 个）      把内部 Service 包成 IntentTool —— 模型能调用的"手"
② 意图规范（YAML，1 份）        标识 / 输入 / 编排 / 输出 / 治理 —— 模型要做的"事"
③ 事实规则（YAML，可选 0~1 份） 这个入口什么时候该出现、带什么数字 —— "什么时候提醒"
```

**不要写**：Controller（平台已提供）、前端页面（面板由 SDK 渲染）、权限判断（宿主 Service 自带）。

---

## 1. 第 0 步：想清楚五要素

写代码之前先填这张表，填不出来说明这个意图还不成立：

| 要素 | 问题 | 反例 |
|------|------|------|
| ① 标识 | 用户点它是要做什么？（`系统.域.动作`） | ❌ `ai.helper.chat`（太泛，等于聊天框） |
| ② 输入 | 必须知道哪些参数才能开始？哪些能从当前页面拿到？ | ❌ 让用户手输 ID（页面已经选中了） |
| ③ 编排 | 需要查哪些事实？**权限边界到哪**？ | ❌ 允许它调用全部工具（越权面不可控） |
| ④ 输出 | 结果长什么样？用户看完要做什么？ | ❌ 输出一段散文（UI 渲染不了，也点不动） |
| ⑤ 治理 | 谁能用？超时多久？失败重试几次？ | ❌ 高危操作配 `roles: ["*"]` |

> **好的意图是"一件能做完的事"**：「把这个账号停用」是意图；「帮我管理用户」不是。

## 2. 第 1 步：写宿主工具

### 2.1 最小实现

在业务模块新建一个 `@Component`，继承 `BaseHostTool`（`ruoyi-intent` 模块里提供）：

```java
@Component
@RequiredArgsConstructor
public class MyOrderQueryTool extends BaseHostTool {

    private final IOrderService orderService;   // 直接注入宿主 Service

    @Override
    public String name() {
        return "my_order_query";                // 必须匹配 ^[a-z][a-z0-9_]*$
    }

    @Override
    public String description() {
        // 这段文字直接进模型提示词，决定模型会不会正确使用它 —— 写清楚"能回答什么问题"
        return "按客户、状态、时间范围查询订单，返回订单号、金额、状态与创建时间。"
             + "用于订单盘点、逾期排查。";
    }

    @Override
    public Map<String, Object> parameters() {
        Map<String, Object> properties = new LinkedHashMap<>();
        properties.put("customerId", Schemas.string("客户编号"));
        properties.put("status", Schemas.enumeration(List.of("0", "1", "2"), "订单状态"));
        properties.put("limit", Schemas.number("返回条数上限，默认 20"));
        return Schemas.object(properties, List.of());
    }

    @Override
    protected Map<String, Object> run(Map<String, Object> args) throws Exception {
        Long customerId = num(args, "customerId");
        int limit = Math.min(intOr(args, "limit", 20), 50);

        List<Map<String, Object>> rows = new ArrayList<>();
        // …调用 orderService，组装 rows…
        return result(rows.size(), rows, null);   // { total, returned, rows, note }
    }
}
```

装完重启即可在启动日志看到 `[intent] 注册宿主工具: my_order_query - …`。

### 2.2 写工具的六条纪律

1. **只读优先**。写操作要三重护栏（显式确认 + 二次鉴权 + 复用宿主校验），参考 `SysUserToggleStatusTool`。
2. **有界查询**。工具会被同步调用，禁止 `selectList()` 全表；用 `PageQuery(limit, 1)` 并设上限。
3. **截断要说清楚**。返回 `note` 说明"命中 N 条，仅返回前 M 条"，否则模型会把样本当全量。
4. **敏感字段自己脱敏**。密钥类一律掩码，返回"是否已配置"而不是值（参考 `SysConfigLookupTool`）。
5. **异常交给基类**。抛出的异常会被转成"错误工具结果"回传模型，让它自行纠正重试——不要自己吞掉。
6. **`description` 就是提示词**。写"能回答什么问题、返回哪些字段、什么时候用"，比写"查询订单"有效得多。

### 2.3 用 `BaseHostTool` 的入参/结果助手

```java
str(args, "k") / strOr(args, "k", "默认")     // 字符串
num(args, "k") / intOr(args, "k", 10)        // 数字
boolOr(args, "k", false)                     // 布尔
strList(args, "k")                           // 字符串数组

row("label", v1, "count", v2)                // 保序的一行
result(total, rows, note)                    // 标准结果信封
cap(rows, 50)                                // 截断
```

## 3. 第 2 步：写意图规范

在业务模块的 `src/main/resources/intent/` 下新建**一个意图一个文件**（`<意图编号>.yaml`）：

```yaml
# ruoyi-modules/ruoyi-order/src/main/resources/intent/order.overdue.scan.yaml
id: order.overdue.scan            # 必填：三段式，小写字母/数字/连字符
name: 逾期订单诊断                 # 必填
description: 盘点逾期订单，按客户与金额分级，给出催收优先级
aliases:                          # 可选：用户可能怎么说（≤8 条，每条 ≤24 字）
  - 有没有逾期订单
  - 催收优先级
version: 1
scope: local                      # local | remote | composite（remote 需 targetSystem）
pages:                            # 只在这些页面出现；空 = 全局意图
  - order/list
  - order/list/*
  - ""

cardType: analysis                # 渲染契约提示（面板按 blocks 渲染，此字段供扩展）
promptTemplate: |                 # 必填：系统提示词主体
  你是订单风控分析员。先调用 my_order_query 取逾期订单事实，禁止编造数据。
  输出要求：
  1. 结论先行：一句话给出逾期总额、涉及客户数、最紧急的一笔；
  2. 用 table 列出 TOP 逾期订单（订单号、客户、金额、逾期天数）；
  3. 用 badges 标出风险等级（danger = 逾期 > 30 天且金额 > 10 万）；
  4. 给出 3 条催收建议，每条点明"联系谁 + 说什么 + 依据的数字"；
  5. 数字缺失就写"数据不足"，不要推测。

paramsSchema:                     # 入参 JSON Schema（必须 type: object）
  type: object
  properties:
    customerId:
      type: string
      title: 客户编号
      description: 留空 = 全部客户
    minDays:
      type: number
      title: 最小逾期天数
      default: 1
  required: []                    # 有必填项时，前端会自动弹补参表单

context:                          # 前端从当前页面自动采集的实体（"上下文即参数"）
  - key: customerId
    title: 当前客户
    required: false

tools: [my_order_query]           # 工具白名单：不写 = 全部工具（不推荐，越权面不可控）

policy:                           # 治理：谁能用、超时、重试
  roles: ["*"]                    # 角色编码或权限串，如 ["order:order:list"]
  timeoutSeconds: 180
  maxRetries: 1                   # ⚠️ SDK 当前未读取，真实重试数来自 intent.llm.output-max-retries
```

### 3.1 校验规则（写错会在启动时直接失败）

| 规则 | 说明 |
|------|------|
| `id` | `^[a-z][a-z0-9-]*(\.[a-z][a-z0-9-]*){2}$` —— **必须是三段** |
| `name` / `promptTemplate` / `scope` | 必填非空 |
| `scope: remote` | 必须同时给 `targetSystem` |
| `paramsSchema` / `outputSchema` | 必须是 `type: object` |
| `tools` | 名字 `^[a-z][a-z0-9_]*$`；**必须已在宿主注册**（启动日志会报 error 提示） |
| `aliases` | ≤ 8 条、每条 ≤ 24 字、不重复 |
| 多文档 `---` | **不支持**：一份文件只能一个意图，多写的会被静默忽略 |

### 3.2 输出规范：只用标准信封

`outputSchema` 留空即使用标准信封，UI 依此渲染。五种 block：

| kind | 字段 | 用于 |
|------|------|------|
| `text` | `text` | 一段说明、层级结构 |
| `kv` | `items[{label,value}]` | 身份信息、指标 |
| `table` | `columns[]` + `rows[][]` | 清单、对比 |
| `list` | `items[{label,value}]` | 待办、步骤 |
| `badges` | `items[{label,value}]` + `level` | 风险标记（info/warning/danger） |

外加两个"下一步"通道：

- `followups: string[]` —— 还需要人工核实/补充的事项（3~5 条）；
- `nextIntents: [{intentId, title, reason, params}]` —— **推荐的下一个意图**，
  `intentId` 必须来自目录，`params` 会作为它的初始入参。

> 写好这两个字段，用户执行完一个意图就能顺着往下走 —— 这是"意图流"的关键。

### 3.3 可选的执行策略：执行器档案（`executor:`）

缺省走 `builtin-agent`（模型现场规划 + 推理循环），适合需要临场判断的分析类意图。
如果某个意图的"怎么做"是固定的（取数看板、巡检快照、标准对账），就别让模型去规划 ——
把它固化成 **skill 型执行器档案**，快、省、可审计：

```yaml
# ruoyi-intent/src/main/resources/intent-executor/my-snapshot.yaml
id: my-snapshot
type: skill                     # skill = 确定性步骤；agent = 交给模型
name: 我的巡检快照
steps:
  - name: online
    tool: sys_online_user_query # 工具必须在宿主注册，且在意图 tools 白名单内
    args: { limit: "20" }
  - name: cache
    tool: sys_cache_overview
    args: { includeUnknown: "false" }
output:
  title: 我的巡检快照
  summary: 纯工具步骤，未调用大模型
  blocks: '[{"kind":"text","title":"在线会话","text":"${steps.online.text}"}]'
limits: { outputMaxRetries: 0 }
```

然后在意图规范里写 `executor: my-snapshot` 即可。

**实测成本对比**（同一个"在线会话 + 缓存规模"取数）：

| 执行方式 | 耗时 | token |
|---------|------|-------|
| skill 型（纯工具步骤） | **13ms** | **0** |
| agent 型（推理循环） | 10~15s | 3k~4k |

两个必踩的坑：

1. `blocks` 这类结构化字段的模板**必须以 `[` 或 `{` 开头**，否则渲染结果被当成纯文本，
   出参 Schema 校验报 `$.blocks: 应为数组`；
2. JSON 模板里的变量占位符**必须自带引号**：`"text":"${steps.online.text}"`，
   不能写 `"text":${steps.online.text}` —— 渲染器会对变量值做 JSON 转义并去掉首尾引号，
   引号要由模板自己补回来。

> 档案与意图规范一样支持**保存即热更新**：后台改完执行器档案，已上线的意图立刻换执行策略，
> 不用发版、不用重启（`ExecutorProfileRegistry#applyTo` 会注销/注册到运行时）。

## 4. 第 3 步：写事实规则（可选，但强烈建议）

**没有规则的意图 = 用户必须自己想起来去点它。** 有规则，它才会在合适的页面、合适的时机主动出现。

### 4.1 先提供事实（Java）

```java
@Component
@RequiredArgsConstructor
public class OrderIntentFactProvider implements IntentFactProvider {

    private final IOrderService orderService;

    @Override
    public List<DatasetSpec> datasets() {
        Map<String, String> fields = new LinkedHashMap<>();
        fields.put("id", "订单编号");
        fields.put("no", "订单号");
        fields.put("customerName", "客户名称");
        fields.put("overdueDays", "逾期天数");
        return List.of(DatasetSpec.of("order.overdue",
                "逾期订单事实（按逾期天数倒排），用于识别需要催收的订单", fields));
    }

    @Override
    public boolean supports(String datasetId) {
        return "order.overdue".equals(datasetId);
    }

    @Override
    public List<Map<String, Object>> rows(String datasetId, IntentCatalogContext ctx, int limit) {
        // 只取数，不做判断；有界查询；按需在 rows 里带 id 字段（用于去重 key）
        return orderService.selectOverdue(limit).stream().map(o -> {
            Map<String, Object> row = new LinkedHashMap<>();
            row.put("id", o.getId());
            row.put("no", o.getNo());
            row.put("customerName", o.getCustomerName());
            row.put("overdueDays", o.getOverdueDays());
            return row;
        }).toList();
    }

    @Override
    public int count(String datasetId, IntentCatalogContext ctx) {
        // ⚠️ 徽标 {{count}} 用的是这里；要与规则 filter 的阈值口径一致
        return (int) orderService.countOverdue();
    }
}
```

> **多个模块**的事实源由 SDK 的 `CompositeIntentFactProvider` 自动聚合并按数据集名分发，
> 你只需要声明自己的 Bean。

### 4.2 再写规则（YAML）

在业务模块的 `src/main/resources/intent-rules/` 下新建（**文件名前缀 = 待办的展示优先级**）：

```yaml
# 10-order-overdue.yaml
- id: order.overdue.remind
  intent: order.overdue.scan                 # 必须已注册，否则启动失败
  dataset: order.overdue
  scope:
    page: ["order/list", "order/list/*", ""] # 只在这些页面提示；"" = 意图中心
  filter:                                    # 行过滤（空 = 全取）
    all:
      - { op: gte, left: row.overdueDays, right: 7 }
      - { op: gt, left: row.overdueDays, right: 30 }
  badge:                                     # 徽标（可选）
    text: "{{count}} 笔订单已逾期"
    level: warning                           # info | warning | danger
  items:                                     # 可点条目（可选，badge 与 items 至少一个）
    limit: 5
    title: "订单 {{row.no}} 已逾期 {{row.overdueDays | days}} 天"
    subtitle: "客户「{{row.customerName}}」· 点击做逾期诊断"
    reason: "逾期订单建议尽早介入，避免拖成坏账"
    params:                                  # 参数映射：key 必须在目标意图的入参 Schema 内
      customerId: { from: row.customerId, type: string }
      minDays: { value: 7 }
```

### 4.3 规则语法速查

**算子**：`eq` `ne` `gt` `gte` `lt` `lte` `in` `contains` `isNull` `notNull`

**取值**：

| 写法 | 含义 |
|------|------|
| `row.xxx` | 当前行的字段 |
| `ctx.userId` / `ctx.page` / `ctx.objectId` / `ctx.objectName` | 上下文（可用字段见下） |
| `now()` / `today()` | 当前时刻 / 今天（按 `intent.time-zone`） |
| `daysUntil(row.endTime)` | 距今还有几天（负数 = 已过期） |
| `30` / `"文本"` | 字面量 |

**模板**：`{{row.xxx}}`、`{{ctx.xxx}}`、`{{count}}`；过滤器白名单：
`date`（yyyy-MM-dd）、`expiryText`（到期文案）、`money`（千分位）、`days`（整数天）。

**可用的 `ctx.*` 字段**（写错会被启动校验拦住）：
`userId` `userName` `tenantId` `page` `objectType` `objectId` `objectName` `today` `now` `count`

**参数映射**：`{ from: row.x, type: string }` 或 `{ value: 常量 }`。
`type` 用于把数字型主键转成 Schema 要求的类型——**Schema 写 `type: string` 就必须 `type: string` 转换**，
否则点击后会被 JSON Schema 校验拒绝。

### 4.4 三条由 SDK 强制的边界（宿主不必自己防）

1. 徽标只挂当前页面**已装载**的意图；
2. 建议引用的意图必须在用户**可见集合**内，否则整条丢弃（下架/无权限的意图不会从建议通道漏出）；
3. 条目型建议的**必填参数必须齐备**（规则映射 + 页面上下文能补上）——不会出现"点了报缺参"的死入口。

### 4.5 事实求值的性能纪律

规则求值发生在目录接口的**同步链路**上（默认按 `intent.suggestions.cache-seconds` 缓存 30 秒）。
因此：**只做轻量查询**（计数 / 近 N 条），单个事实源异常会被 SDK 隔离，不会拖垮目录接口。

## 5. 第 4 步：前端（业务页面 4 行）

如果意图的必填参数能从当前页面拿到，用户点开面板就能直接执行，**不需要填任何东西**：

```ts
<script setup lang="ts" name="Order">
import { registerIntentPageContext } from '@/views/intent/pageContext';

/** 当前选中行（页面已有的状态） */
const currentRow = ref<OrderVO>();

let unregisterIntentContext: (() => void) | undefined;

onMounted(() => {
  unregisterIntentContext = registerIntentPageContext('order/list', () => ({
    // 入参 Schema 声明为 string 时记得 String(...)
    customerId: currentRow.value ? String(currentRow.value.customerId) : undefined,
    orderNo: currentRow.value?.no
  }));
});

onBeforeUnmount(() => {
  unregisterIntentContext?.();
});
</script>
```

**为什么必须由页面注册而不是面板去猜**：面板与页面必须看到**同一份数据**。
如果面板去猜路由参数或重新查一次库，就会出现"面板分析了另一个对象"的张冠李戴。

### 5.1 面板挂载点

- **全站浮标**：已挂在 `src/layout/index.vue`（`<intent-floating />`），业务页面不用管；
- **页面内嵌面板**：`IntentUI.mount({ container: el, page: 'order/list', mode: 'debug' })`（见意图调试台）；
- **按指定页面强制装载**：`IntentUI.mountFloating({ getPage: () => 'order/list' })`；
- **口语匹配**（可选）：`IntentUI.match('有没有逾期订单')` 返回 `[{entry, score, hit}]`，可做搜索框高亮。

### 5.1.1 换页时必须还原面板（一个必须知道的坑）

悬浮入口是**全站常驻**的（挂在 layout 上），**切换菜单不会让它重新挂载**，面板状态会跨页面一直存活。
如果不处理，用户会遇到这种情况：

```
在「用户管理」点了一个意图 → 看到结果卡
→ 切到「字典管理」→ 再打开浮标
→ 结果卡还在，看起来像是"在字典页跑出来的" —— 上下文串页
```

SDK 已经处理了最常见的一条路径：**重新打开抽屉时发现页面变了，会自动清空运行态再拉新页目录**
（`Panel#reset()` 清掉结果卡、选中项、报错、分组折叠、待办翻页、匹配框输入；
刻意保留 `entityCache`（实体下拉候选）与 `rated`（已评价标记），它们与页面无关）。

但**宿主还必须自己接一条线**：抽屉开着的时候路由被改掉（浏览器前进后退、代码里 `router.push`、重定向）
——这条路径 SDK 看不到，需要宿主监听路由并主动还原。框架已内置：

```ts
// src/views/intent/components/IntentFloating.vue
watch(
  () => currentIntentPage(route.path),
  (page, previous) => {
    if (!floating || page === previous) return;
    if (floating.isOpen()) floating.close();   // 换页不留着上一页的面板
    floating.reset();                          // 重开即是干净的
  }
);
```

新增的两个 SDK 句柄方法（`mount` / `mountFloating` 都返回）：

| 方法 | 作用 |
|------|------|
| `reset()` | 清空运行态（结果卡 / 选中项 / 报错 / 分组折叠 / 待办翻页 / 匹配框），保留与页面无关的缓存 |
| `page()` | 返回面板当前已装载的页面标识（宿主据此判断"是不是真的换页了"） |

> 如果你的业务页面是**同一个路由路径**下的不同对象（例如 `/order/list` 里切换客户），
> 路由不会变，面板也就不会重置 —— 这是对的：此时"留上下文"正是想要的。
> 需要在对象切换时也清空结果卡的话，在页面里拿到选中行变化后调用一次 `floating.reset()` 即可。


### 5.2 实体下拉（可选）

对于用户需要手工选择的参数（如"选一个客户"），在 `src/views/intent/sdk.ts` 的 `entityOptions` 里加一行：

```ts
customerId: () => safeOptions(
  () => request({ url: '/order/customer/simple-list', method: 'get' }),
  row => ({ label: row.name, value: String(row.id) })   // ← 记得 String(...)
)
```

面板会自动给该参数渲染一个 ⚙ 按钮，点开就是候选列表。

### 排障速查

| 现象 | 原因与处理 |
|------|-----------|
| 启动日志 ERROR：`意图 X 声明的宿主工具未注册: Y` | 工具 Bean 没被扫描到（包名必须在 `org.dromara.*`），或 `tools` 里写错了名字 |
| 后台删掉某个意图，重启后**没有**被种子复活 | **这是设计行为**：播种只在物理不存在时写入（含逻辑删除态判定）。确实要用回内置种子，需先物理删掉 `del_flag=1` 的那行 |
| 意图点了报 `EXECUTOR_NOT_FOUND` | 规范里的 `executor:` 指向的档案不存在或已被删；后台「执行器档案」页能看到已注册清单 |
| 出参校验报 `$.blocks: 应为数组` | 见 3.3 的两个坑（模板要 `[` 开头 + 占位符自带引号） |
| 目录里看不到徽标 / 待办 | 规则 `scope.page` 没覆盖当前页面；或 `{{count}}` 口径（`FactProvider#count`）与 `filter` 阈值不一致 |
| 待办出现了但点开报缺参 | 规则的 `items.params` 没把必填参数映射齐（启动校验会拦，但改完规范后要重启才校验） |
