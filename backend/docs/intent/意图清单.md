# 意图即服务 · 开箱即用意图清单

> 本清单是 `ruoyi-intent` 模块的交付内容：**14 个意图 / 13 个宿主工具 / 1 个执行器档案 / 3 个事实数据集 / 3 条声明式事实规则**。
> 它们不是 demo，而是把 RuoYi-Vue-Plus 既有的系统管理与监控能力，用"意图"的方式重新组织了一遍。

---

## 1. 为什么选这批能力

意图即服务最适合的场景有三个特征：**取数分散**（要翻好几个页面）、**判断有套路**（老手心里有清单）、**结论要落到动作**（看完得做点什么）。
系统管理与监控恰好三条全中：

| 传统做法 | 意图做法 |
|---------|---------|
| 账号盘点要翻用户列表 + 登录日志 + 角色表，靠经验判断 | 「账号风险体检」一次跑完四个维度，输出带数字的风险清单 |
| 「这个权限是干什么的」要问老同事 | 「权限译解」把权限串翻译成业务语言，并列出谁拥有它 |
| 登录异常要人工对着日志数失败次数 | 「登录异常分析」自动识别爆破、异地、失败后成功链 |
| 参数与客户端策略散落在两处配置页 | 「参数配置审计」「终端接入体检」逐条给合规结论 |

## 3. 宿主工具清单

工具即"模型能调用的手"。**13 个工具全部是只读的，只有 1 个写工具，且带三重护栏。**

| 工具名 | 类 | 数据来源 | 关键设计 |
|--------|----|---------|---------|
| `sys_user_query` | `SysUserQueryTool` | `ISysUserService#selectPageUserList` | 口径与用户管理列表一致；最多 50 条并说明截断 |
| `sys_user_profile` | `SysUserProfileTool` | `ISysUserService` | 单账号全景；算出 `roleGroup` / `postGroup` |
| `sys_user_toggle_status` | `SysUserToggleStatusTool` | `ISysUserService#updateUserStatus` | **写操作**：`confirm=true` 才落库 + `StpUtil.checkPermission` 二次鉴权 + 复用 `checkUserAllowed`/`checkUserDataScope` |
| `sys_role_matrix` | `SysRoleMatrixTool` | `ISysRoleService` + `ISysMenuService` | 角色 → 权限串 → 成员数一次取全；默认只回权限样例防爆上下文 |
| `sys_menu_search` | `SysMenuSearchTool` | `ISysMenuService#selectMenuList` | 支持权限串 / 菜单名 / 路由三种口径检索 |
| `sys_dept_tree` | `SysDeptTreeTool` | `DeptService#selectDeptsByList` | 树形或平铺；每部门在册与停用人数 |
| `sys_dict_lookup` | `SysDictLookupTool` | `ISysDictTypeService` | 顺带给出"空字典 / 缺备注"等体检事实 |
| `sys_config_lookup` | `SysConfigLookupTool` | `ISysConfigService` | **敏感键名一律掩码**，只暴露"是否已配置" |
| `sys_client_lookup` | `SysClientLookupTool` | `ISysClientService` | token 超时策略其实在 `sys_client` 表里，不在 yml —— 工具直接给出，省掉一次找错地方 |
| `sys_login_log_query` | `SysLoginLogTool` | `ISysLoginInfoService` | 有界回溯 300 条，内存内按时间窗聚合，给出失败 TOP 账号/IP |
| `sys_oper_log_query` | `SysOperLogTool` | `ISysOperLogService` | 成功/失败统计、失败模块 TOP、最慢耗时 |
| `sys_online_user_query` | `SysOnlineUserTool` | `RedisUtils` + Sa-Token | token 只回脱敏后缀，**完整 token 不进提示词** |
| `sys_cache_overview` | `SysCacheOverviewTool` | `RedisUtils.keys` | **只回数量不返回值**（缓存里有会话与业务数据） |

### 写工具的三重护栏（`SysUserToggleStatusTool`）

```java
// ① 显式确认：confirm=false 时只返回影响预览，不落库
// ② 二次鉴权：即使模型被提示词注入诱导，也越不过宿主权限
StpUtil.checkPermission("system:user:edit");
// ③ 宿主既有校验：与后台按钮走同一条路（禁止操作超管 + 数据权限）
userService.checkUserAllowed(userId);
userService.checkUserDataScope(userId);
```

意图侧的 `policy.roles` 也收窄到 `["system:user:edit"]`，形成"意图可见性 + 工具执行"双保险。

## 3.1 执行器档案：把"用哪个模型、几步做完"变成数据

`resources/intent-executor/*.yaml` 声明执行器档案，启动播种进 `intent_executor` 表，
后台改完**保存即热更新到运行时**（不用发版、不用重启）。意图规范用 `executor: <id>` 引用它。

| 档案 | 类型 | 用途 | 成本特征 |
|------|------|------|---------|
| `system-health-snapshot` | `skill` | 顺序执行 2 个只读工具步骤，返回在线会话与缓存规模 | **零 token / 13ms**，不调用大模型 |

```yaml
id: system-health-snapshot
type: skill                       # skill = 确定性步骤；agent = 交给模型现场规划
steps:
  - name: online
    tool: sys_online_user_query   # 工具必须在宿主注册，且需在意图的 tools 白名单内
    args: { limit: "20" }
output:                           # 出参模板：渲染成前端可渲染的标准信封
  title: 系统健康快照
  summary: 已取回在线会话与缓存规模（纯工具步骤，未调用大模型）
  blocks: '[{"kind":"text","title":"在线会话明细","text":"${steps.online.text}"}]'
limits: { outputMaxRetries: 0 }
```

> ⚠️ **两个必须知道的坑**（都实测踩过）：
> 1. `blocks` 这类结构化字段的模板**必须以 `[` 或 `{` 开头**，否则渲染结果会被当成纯文本，
>    出参 Schema 校验直接报 `$.blocks: 应为数组`；
> 2. JSON 模板里的变量占位符**必须自带引号**：写 `"text":"${steps.online.text}"`，
>    不能写 `"text":${steps.online.text}` —— 渲染器会对变量值做 JSON 转义并去掉首尾引号，
>    引号要由模板自己补回来。

## 4. 声明式事实规则

3 条规则让意图入口从"能力列表"变成"待办列表"。**改阈值、改文案、改挂载页面只动 YAML。**

| 规则文件 | 数据集 | 目标意图 | 徽标 | 触发条件 |
|---------|--------|---------|------|---------|
| `10-system-inactive-user.yaml` | `system.inactive-users` | `system.user.risk-scan` | `{{count}} 个账号超过 30 天未登录`（warning） | 在册 + 距上次登录 ≥ 30 天 |
| `20-system-login-failure.yaml` | `system.login-failures` | `monitor.login.anomaly` | `近 24 小时 {{count}} 次登录失败`（danger） | 单账号 24h 内失败 ≥ 3 次 |
| `30-system-empty-role.yaml` | `system.empty-roles` | `system.permission.audit` | `{{count}} 个角色没有任何成员`（info） | 角色成员数为 0 |

### 事实数据集

| 数据集 | 提供者方法 | 字段 | 口径与边界 |
|--------|-----------|------|-----------|
| `system.inactive-users` | `SystemIntentFactProvider#inactiveUsers` | `id userName nickName deptName status idleDays lastLogin` | 最多扫 500 个账号；`idleDays = -1` 表示从未登录 |
| `system.empty-roles` | `#emptyRoles` | `id roleKey roleName status memberCount` | 全量角色，逐角色计成员数 |
| `system.login-failures` | `#loginFailures` | `id userName failCount lastIp lastTime` | **有界样本**：回溯最新 200 条失败日志，按账号聚合 |

> ⚠️ **徽标数字的口径**：`{{count}}` 用的是 `IntentFactProvider#count()`，**不是** filter 之后的条数。
> 所以 `countInactive()` 里的 `>= 30` 必须与规则里的 `idleDays >= 30` 对齐 —— 这是这套机制里唯一容易踩的坑，
> 已在本框架中显式对齐并在代码注释里标注。

### 挂载页面分布（规则里的 `scope.page`）

```
system/user        账号体检徽标 + 久未登录待办 + 僵尸角色待办
system/role        僵尸角色待办 + 久未登录待办
system/backlog     （如接入工作台页可自行追加）
monitor/logininfo  登录失败徽标 + 失败账号待办
monitor/online     登录失败待办
""（意图中心）      全部待办（不按页面过滤）
```

**系统管理页之外不打扰**：例如在监控页不会弹出"账号该停用了"，避免挤占当页更相关的建议。

## 5. 建议的下一步意图（留给业务的扩展位）

按同样的模式，可以直接复制出这些意图（每个约 1~1.5 人日）：

| 域 | 建议意图 | 需要新增的工具 |
|----|---------|--------------|
| 代码生成 | `gen.table.audit` 表结构体检（缺注释、无主键、命名不规范、字段类型风险） | `gen_table_inspect` |

| 文件 | `oss.storage.audit` 存储审计（大文件、孤儿文件、类型分布） | `oss_file_query` |
| 通知 | `notice.reach.analyze` 通知触达分析（谁没读、哪条没人读） | `notice_read_query` |
| 消息 | `message.failure.triage` 消息发送失败归因 | `message_log_query` |
| 数据权限 | `permission.data-scope.map` 数据范围可视化（谁能看到谁的数据） | `data_scope_resolve` |

> 扩展时的纪律还是那三条：**工具只读优先且要有界**、**规范写在 YAML 且启动强校验**、
